# Metricool Scheduling

Metricool is the scheduler for all of Joe's brand social accounts. Access is via a **hosted OAuth MCP server** (`https://ai.metricool.com/mcp`, auth=oauth) connected to the `joeagent` profile. 7 tools: `getBrandSettings`, `getScheduledPosts`, `createScheduledPost`, `updateScheduledPost`, `getAnalyticsDataByMetrics`, `getAnalyticsAvailableMetrics`, `getBestTimeToPostByNetwork`.

This skill owns the **publish/schedule** step — turning finished copy into a scheduled or draft post on the right brand. Generation of the copy itself lives in other skills (linkedin-posts, podcast skills). When asked to "write a caption AND schedule it," do the caption, then come here for the scheduling mechanics.

## ⚠️ The Metricool MCP is kept DISABLED by default — enabling it needs a session RESTART to load the tools (July 2026)

Joe's standing posture: `mcp_servers.metricool.enabled: false` in config (memory rule — keeps the ~179s token probe from popping constantly). Operational consequence when a session needs to schedule:
- **`hermes config set mcp_servers.metricool.enabled true` does NOT hot-load the tools into the RUNNING session.** MCP tools load at session startup only. So flipping the flag mid-session leaves the `metricool_*` tools absent — you'll confirm the config changed but still can't call them. **Tell Joe to restart the session (or `/new`) after enabling**, then the tools are available. (Toggling config on/off is instant on disk; the tool *loadout* is fixed at launch.)
- **Standard cycle for a one-off scheduling job:** (1) `hermes config set …enabled true`, (2) Joe restarts, (3) do all the scheduling, (4) `hermes config set …enabled false` again to restore the default-off posture. Do step 4 when the scheduling work is done — don't leave it enabled.
- This is DISTINCT from the "tools not loaded even though server shows enabled" pitfall below (that one is a load quirk with an already-enabled server, fixed via the HTTP bridge). Here the server was deliberately OFF and the fix is simply enable + restart.

## Campaign CADENCE & calendar layout (Joe corrected HARD, June 2026 — multi-idea episode/batch campaigns)

When laying a multi-idea batch onto the planner (e.g. an episode's 4 ideas × 3 platforms), the SCHEDULING SHAPE matters to Joe as much as the content:
- **TWO IDEAS PER DAY, not one.** Joe rejected a one-idea-per-day spread across 4 days. Pack 2 ideas into each day.
- **MIX A VIDEO IDEA WITH A POSTER IDEA each day — for format variety in the daily feed.** Don't put all the video ideas on day 1–2 and all the poster ideas on day 3–4; consecutive days then look the same. Each day pairs one motion idea + one static-poster idea so the feed never shows the same *species* of asset twice in a row.
- **START TODAY, not tomorrow.** Joe expects the campaign to begin on the CURRENT day when an open slot remains — he caught "posts should have started Monday not Tuesday." Before scheduling, print the real current weekday/date from Python `zoneinfo` and use today as day 1 if a future slot remains.
- **Stagger times within a day so the paired ideas don't collide:** e.g. video idea 11:00 / 13:00 / 17:00 (LI/IG/FB), poster idea 12:00 / 15:00 / 17:30 — offset ~1 hr per platform.
- **Rescheduling is cheap — don't rebuild.** When Joe corrects cadence/start-day after drafts exist, just `updateScheduledPost` each draft's `publicationDate` (carry the full original `info`, change only the date); media stays attached. Don't regenerate assets to move a date.
- **DAYTIME ET ONLY — never schedule into the night (Joe corrected HARD, June 2026).** When fixing a too-tight spacing or a collision, the fix is a different DAYTIME slot, NOT pushing a post to the evening. I moved two SM posts to 7:00 PM / 8:30 PM ET to dodge a \"date in the past\" risk on the earlier slot and Joe pushed back immediately: *\"why move the posts to night time… we are not just aimlessly posting, we need to make posts when people will be able to see it.\"* Keep posts inside the ~8 AM–5 PM ET working-audience window. If the only conflict-free slot you can find is at night, you're spacing wrong — re-space the whole day's posts across the daytime band (or spread across more days) rather than parking one after hours.
- **3-HOUR MINIMUM between posts on the SAME platform same day — applies to EVERY network, not just Facebook (Joe rule, June 2026).** Two posts to the same page within ~30–60 min looks spammy and splits their reach. Joe first flagged it on Facebook (\"two posts just 30 mins or an hour apart doesn't make much sense\") then generalized it: *\"the rule should also apply for all other platforms — minimum of 3 hrs between posts.\"* Different PLATFORMS at the same timestamp are fine (an IG post + an FB post at 3 PM is normal); the 3 hr floor is per-network. Make a same-platform <3hr-gap check part of the final verification sweep alongside the same-timestamp collision check.
- **⛔ ENFORCE SPACING AT CREATION TIME, not just in the final sweep (Joe corrected HARD, July 2026).** The failure: I scheduled 2 feed posts at the same 8:29am and 3 feed posts at the same 8:00am — all same-platform same-timestamp double-books — then only caught it in verification. Joe: *"why have you scheduled two posts for the same time, rectify that now."* Each IDEA that hits the same networks needs its OWN distinct time slot BEFORE you fire the create calls — never batch-create multiple ideas at one timestamp intending to space them later. His preferred simple shape when he says "N posts, spaced": ONE idea per time slot, that idea's feed post + its story fire together at that slot (story exempt from the 3-hr rule), and consecutive ideas sit hours apart in the daytime band. E.g. 2 ideas/day → 8:30am + 1:00pm; 3 ideas/day → 8:30am + 1:00pm + 5:00pm. Compute the distinct slots first, then create each idea's posts at its own slot. (Rescheduling to fix it is cheap via `updateScheduledPost` — carry full `info`, change only `publicationDate`, key by `uuid` — but doing it right at creation avoids the correction.)
- **STORIES are EXEMPT from the 3 hr rule, and a story fires at the SAME TIME as the feed post it's paired with (Joe rule, June 2026).** A Story and its companion feed post are different placements that reinforce each other — no collision, no spacing needed. Each story just inherits its paired post's exact `publicationDate`. Stories = IG + Facebook only (and Joe's personal brand has NO Facebook connected → JD stories are IG-only); confirm connected networks with `getBrandSettings` before scheduling stories, don't assume.

## Standard scheduling workflow

⚠️ **Hosted-server API schema CHANGED (June 2026) — read `references/per-platform-batch-scheduling.md` top section BEFORE building any `createScheduledPost`/`getScheduledPosts` payload.** Short version: `createScheduledPost` now takes `{blogId, date, info}` where `info` is a **json.dumps STRING** (not an object, no top-level brandId/autoPublish); `getScheduledPosts` takes `brandId` as a **string** + `timezone` + `fromDate`/`toDate`, returns a JSON string. **`blogId` must be a STRING too** (`'6425321'`, not the int `6425321`) — an int blogId hard-fails with `Validation failed: structuredContent does not match tool outputSchema ... /blogId: integer found, string expected`. Also: run the token keeper `--once` in the SAME chained shell command as a create burst so the ~179s token can't rotate mid-batch (avoids `invalid_grant`).

⚠️ **`invalid_grant` has TWO distinct causes — disambiguate by reading the token file, don't just retry (observed June 2026).** (1) MID-BATCH ROTATION: the ~179s token rotated between calls; the warm-call / token-keeper-`--once`-in-the-same-chained-command trick fixes it. (2) SPENT/EXPIRED REFRESH: the cached refresh token itself is dead — then EVEN a fresh warm `getBrandSettings` call returns `invalid_grant`, and `mc_bridge`'s silent refresh CANNOT recover it. When the warm call ALSO fails, stop retrying and READ `~/AppData/Local/hermes/profiles/joeagent/mcp-tokens/metricool.json`: if `expires_at` is in the past (`expires_at - time.time() < 0`) the token is genuinely expired and this is cause (2) → it needs a real re-auth via `hermes mcp login metricool` (bound by the no-surprise-auth policy: confirm broken + tell Joe a browser window opens + get his go-ahead first). ## Pitfalls

- **ALL date params REQUIRE a timezone offset — bare ISO datetimes hard-fail, on `createScheduledPost` AND `getScheduledPosts` (re-confirmed July 2026).** Every date arg — `createScheduledPost`'s top-level `date`, and `getScheduledPosts`'s `fromDate`/`toDate` — must be full ISO 8601 *with offset* (e.g. `2026-07-01T08:29:00-04:00`). A bare `2026-07-01T08:29:00` returns `Text '...' could not be parsed at index 19` (index 19 = the char right after seconds, where the offset belongs). NOTE the inner `info.publicationDate.dateTime` is the OPPOSITE — it is a bare `YYYY-MM-DDTHH:MM:SS` string paired with a separate `timezone:"America/New_York"` field (no offset there). So: offset on the top-level `date`, NO offset on `publicationDate.dateTime`. Default to appending the EDT `-04:00` / EST `-05:00` offset on every top-level date arg.
- **Do NOT pass `user_intent` to `createScheduledPost` (in-session MCP tool) — it breaks the OUTPUT-schema validation (verified July 2026).** The `createScheduledPost` tool description asks for a mandatory `user_intent`, but actually including it returns `Validation failed: structuredContent does not match tool outputSchema ... property 'user_intent' is not defined in the schema and the schema does not allow additional properties`. The call may not write the post. Fix: OMIT `user_intent` entirely — call with just `{blogId, date, info}`. First verify nothing was created (`getScheduledPosts`, expect empty `data`) before retrying, so you don't duplicate. (This is the in-session tool quirk; the `mc_bridge` HTTP path uses the same 3-key envelope and never wants `user_intent`.)\n- **`networkData` for a network NOT in `providers` = hard error.** Including e.g. `twitterData` in `info` when `twitter` is not in the `providers` list fails with `networkData contains data for network 'twitter' not listed in providers`.   from zoneinfo import ZoneInfo
  ```python
  ny = datetime.now(ZoneInfo("America/New_York"))
  target = (ny + timedelta(minutes=30)).strftime("%Y-%m-%dT%H:%M:%S")
  ```
  Then build the ISO date with the correct offset (`-04:00` EDT / `-05:00` EST).
